# US-22.3 Video Rendering Progress and Delivery — live demo (PR #364)

*2026-07-28, driven by an httpx client against the real FastAPI app with real
MongoDB and real local storage, serving a genuinely playable MP4.*

Stack: `create_app(settings)` over real MongoDB (27018) + local-filesystem
storage. The source render is a real **1280×720 H.264 + AAC** MP4 generated by
ffmpeg and stored at the video's `storage_path`; every served byte is the real
file, verified with `ffprobe`. No live video provider exists in this environment
(same disclosure as US-22.1/22.2), so the render *pipeline* doesn't advance
here — the delivery endpoints are exercised against a seeded `Video` + MP4,
which is exactly what they serve in production. AC2's cross-navigation
notification is a client behavior proven with outcome evidence by
`web/contexts/video-jobs-context.test.tsx` (the `notify` mock receives the
`video_complete` payload from the app-level watcher's poll loop).

## Driver transcript (every assertion is against the live endpoints)

```
# Source render: a real 720p H.264+AAC MP4 (54994 bytes)
  ffprobe: codec_name=h264 | codec_type=video | width=1280 | height=720 | codec_name=aac | codec_type=audio

## AC3 — Completed video is playable in-browser
  GET /videos/{id}/stream -> 200, content-type=video/mp4, accept-ranges=bytes, 54994 bytes
  served bytes are a real playable MP4 -> ffprobe: h264 video | 1280x720 | aac audio
  VERIFIED: the streamed bytes are the exact render and decode as h264 video + aac audio
  GET .../stream Range bytes=0-99 -> 206, content-range=bytes 0-99/54994, 100 bytes
  VERIFIED: Range request returns 206 partial (seekable player)

## AC4 — Download produces a valid MP4 with correct resolution and audio
  GET .../stream?download=1 -> 200, content-disposition='attachment; filename="video-{id}.mp4"'
  downloaded file -> ffprobe: width=1280 height=720 h264 + aac audio
  VERIFIED: attachment download decodes to 1280x720 h264 + aac audio

## AC5 — Publish makes the video visible on the song detail page
  before publish: GET /videos/for-clip/{clip} -> 404 (song page shows NO video section)
  POST /videos/{id}/publish -> 200, published=True
  after publish: GET /videos/for-clip/{clip} (anonymous) -> 200, returns the video
  anonymous GET .../stream -> 200, 54994 bytes
  VERIFIED: publish flips the song page from no-video to a playable, anonymously-viewable music video

## AC1 — Progress bar updates during rendering (>= every 5s)
  GET /videos/{job}/status -> status=rendering, progress=20%, eta=90.0s
  GET /videos/{job}/status -> status=rendering, progress=55%, eta=40.0s
  GET /videos/{job}/status -> status=encoding,  progress=92%, eta=8.0s
  GET .../status (finished) -> status=complete, progress=100%, video_id set
  VERIFIED: status reports live rendering->encoding->complete with %+ETA; the web hook polls every 2.5s (< 5s)

## AC2 — Completion notification if the user navigated away
  The app-level VideoJobsProvider polls this status endpoint across navigation; on
  status=complete it raises a 'video_complete' notification. The status transition
  above is the data it consumes; the poll->notify->survives-unmount behavior is
  proven by contexts/video-jobs-context.test.tsx.
```

## Notes

- **Visibility** mirrors clip-audio streaming: a video is private to its owner
  until published; a published video streams to anyone who can view its (public)
  clip; an unpublished/unowned video is an indistinguishable 404. A published
  video on a still-private clip stays 403 for an authenticated stranger.
- **Streaming** currently buffers the whole object before slicing a Range (same
  as clip audio). Fine for these sizes; a streaming/partial-read `StorageBackend`
  API is tracked as a follow-up (#365) for large 1080p/4K renders.
- **Social export** (per-platform 16:9/9:16/1:1 re-frames) is intentionally
  deferred — not in the acceptance criteria; aspect ratio is chosen at render
  time.
